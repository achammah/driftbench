# Changelog

All notable changes to driftbench are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the versions follow [Semantic Versioning](https://semver.org/). Every package under `packages/` and the Python package `python/driftbench` carry the same version; `node tools/release/check.mjs` verifies it.

## [Unreleased]

* New exports of `@agent-nexus/driftbench-estate`, frozen in `tools/structure/api-surface.json`: `proseCandidates`, `proseCacheKey`, `ProseCache`, `FileProseCache` and `ProseEstimate`, `proseEstimateLine` (the code-found prose candidates and their cache, and the cost line of a model pass); `USER_LAYER` and `isUserLayerPath` (the user-level skill layer); `citationsByFile` and `filesReached` (the estate graph).
* Estate user-level skill layer: a container named `Trash` or `trash` is not read, a relative `--user-skills` folder is relative to the folder the command is typed in, an empty `--user-skills` value or `userSkills` reader option is refused, and the hidden-folder, dependency-folder, trash, `~` and relative-path rules each have a test that fails when the rule is removed.

* The estate reader can read the user-level skill layer as a second skill layer. It is opt-in and never reads a home folder on its own: it reads the folder named by `--user-skills <folder>`, the `userSkills` key of `driftbench.estate.yaml` or the `userSkills` reader option (usually `~/.claude/skills`), so a scan gives the same map on every machine. A scan that read a layer records `userSkills: true`; `estate lint` then needs the folder again. A folder with a `SKILL.md` is a skill, a folder without one is a container read one level deeper, links are followed, hidden folders such as a trash folder are not read, a folder reached twice is one skill, and the project layer wins a name clash. The files of the layer carry the path `~/.claude/skills/...` in the map and are no part of an estate copy. New public names of `@agent-nexus/driftbench-estate`: `USER_LAYER`, `isUserLayerPath`, the `userSkills` option of `readerFor` and `ClaudeCodeReader`, `EstateFile.layer`, `RawEstate.userLayer` and the `userSkills` field of the map.

* Estate routing tables. A cell or header that states what a unit does not do ("It cannot do", "Does not handle", "Cannot book a berth") gives no route: a route comes only from a cell that states when to use the unit. A table of limits only is not ambiguous. A prohibition addressed to the agent ("Do not share the key") is still a rule a table may bind to a unit.

* Estate graph at real size. A skill or helper stores one `reference` edge for each citation in a file it owns (its definition file and, for a skill, the files of its folder its citations lead to) and none for what a shared file cites in turn: an index cited by 57 units and citing 3,500 files stores 57 edges, not 200,000. Reach is computed on demand with the new `filesReached` and `citationsByFile` of `@agent-nexus/driftbench-estate`. The plan command prints the first 10 lines of each list and names the summary file for the rest. A sentence that mentions a path is read once for every spelling of the path.

A prerequisite owned by a helper asks for the work to be handed to a helper, and a shared document is owned by the unit whose file cites it. * The interval of a campaign-level criterion (`--aggregate pass-rate:>=0.8`, `broken-share:<=0.1`) is clustered by golden. It was a Wilson interval on all runs read as independent; it now is the Wilson interval on the effective runs, the same interval the scorecard prints for a pass rate over goldens (`wilson, design effect`, or `wilson, clusters` when every run agrees; one golden, or one run in every golden, keeps the plain Wilson interval). On simulated suites of correlated goldens it holds the true rate in 94.8% of suites (nominal 95%, worst cell 94.0%) where the plain interval held it in 75.2%. `interval` of an aggregate result gains `method`, and over several goldens `clusters`, `designEffect` and `effectiveRuns`; an undecided result also gains `goldensNeeded` (a whole number of copies of the present goldens that would decide it), and `runsNeeded` counts the runs of those goldens. A threshold the plain interval called decided can now be undecided when goldens disagree. Values, `passed`, the verdict and every exit code are unchanged. A custom criterion keeps the plain interval unless its `counts` also give `clusters`. `report` prints the new interval and `action/run.sh` the new planning line. The end-state match tile of the scorecard gets the same interval over goldens (the tile reads 75.8% to 100.0% where it read 90.4% to 100.0% on the Acme example: 12 goldens that all match); the committed `examples/acme/reports/acme.html` and `acme-faults.html` are regenerated from the same campaigns (same data; timings and creation times differ). `pilot-acme-random.html` is regenerated too, by re-running the pilot of `examples/acme/reports/README.md` (two runs agree on every number; only timings differ; 417 runs, 18.7% pass, as before): its end-state tile reads [96.9%, 100.0%] where it read [98.9%, 100.0%].

* Clustered and hierarchical intervals in the report. The suite headline of `driftbench report` is the mean over goldens with the hierarchical interval (method `hierarchical`), printed per mode on the command line (`Suite pass rate, mode F: ...`), as a tile and a column of the scorecard, and in the JSON as `modes[].headline`. It carries `n_eff`, the design effect, the smallest drop two suites like it detect at 80% power, and the share of runs that did not complete (and `blocked` or `not_run` once a run carries those states). A rate over clusters that already used Wilson on the effective sample (`wilson, design effect`) now prints its `n_eff` and design effect beside the interval, and carries `designEffect` and `effectiveN` in the JSON. No pass rate and no hash, cache key or cassette changes; the interval numbers that were printed before are the same, and the rendered scorecard HTML gains the headline and the `n_eff` notes. New in `@agent-nexus/driftbench-report`, added to the frozen API list: `suiteHeadline`, `SuiteHeadline`, `HEADLINE_POWER`, `effectiveNote`, `headlineNote` and `headlineText`. The `pass-rate` and `broken-share` aggregates of `report` and `ci` still read the runs as independent and are not changed here.
* New in `@agent-nexus/driftbench-stats`: `hierarchicalBetaBinomial`, the hierarchical Beta-Bernoulli interval for the mean pass rate of a suite of trees (deterministic: the posterior is read on a fixed grid, with no sampling and no seed); `wilsonEffective`, the Wilson interval on the effective blocks `n_eff` with the design effect from the spread of the cluster rates (the interval the scorecard already printed for a rate over repeats, now as a function that also returns the design effect and `n_eff`); and `simulateCoverage`, which checks the coverage of the interval methods on simulated suites of correlated trees. On the 24 cells the repository test runs (about three seconds, 400 suites per cell): naive Wilson covers 73.9%, Wilson on `n_eff` 91.3% with the normal quantile and 93.1% with the Student t quantile, the hierarchical interval 95.3%. Types `TreeCount`, `HierarchicalOptions`, `HierarchicalInterval`, `ClusterCount`, `EffectiveWilsonOptions`, `EffectiveWilson`, `CoverageCell`, `CoverageOptions`, `CoverageResult` and `CoverageMethod` are added to the frozen API list. Nothing existing changes.
* Mode T on an adapter that sends the history to a model (anthropic, google, http, litellm, langgraph, openai-agents, pydantic-ai, vercel-ai) no longer sends a past tool call without a result as a call that returned `null`. Such a call comes from a canonical prefix when the spec's world forces no result for its tool. The adapter now sends a text result saying the result was not recorded (see [run modes](docs/concepts/run-modes.md#teacher-forced)). Force the tool's result in `world.tools` to give the agent a real one. The function adapter, the canonical prefix and the Given hash are unchanged. These 8 adapters move from version 0.1.0 to 0.1.1, and the block cache key holds the adapter version, so every block cached on them before this change (modes T, F and P alike) is a cache miss and runs again; otherwise a mode T block cached with `null` would replay without the fix. Modes F and P send the same bytes as before for complete recorded histories and the SDK adapters' own loops, which always record a result or an error. One exception: an http endpoint that answers with an Observed may return a `tool_call` segment with no matching `tool_result`; the next request of that run now carries the note where it carried `null`. Found by the H9 Given verifier: over the example specs, 2,688 of 2,698 canonical calls have no result.
* Two block verdicts beside pass and fail: `not_run` (the block was not sent, its Given could not be applied) and `blocked` (an ancestor it depends on failed). `BlockResult` gains optional `status`, `notRun` (`kind` `given_unmet`, `unsupported` or `setup_failed`, `layer`, `check`, `expected`, `got`) and `blocked` (`by`, `root`), written only on such a block, whose `pass` stays false; every record of a pass or a fail is unchanged, byte for byte, and keeps its hash. The runner's always-on `capability` check makes a block `not_run: unsupported` when its Given carries a `prefix` on an adapter without `seedPrefix` or a forced tool result on one without `toolStubs`, where the layer used to be dropped silently; in modes F and P the later blocks are not run either and the end state is not compared. No shipped example spec has such a block on its own target (a new test checks every one). Every pass rate leaves both statuses out and prints their count beside it: campaign cells gain the states `not_run` and `blocked`, the scorecard `notRun` and `blocked` counts, JUnit a `skipped` case, `compare` an unpaired unit `not measured in the candidate`, and the pass-rate aggregate, reliability, spread, succession and the compounding index count scored blocks only. A run with such a block is never carried, and a re-judge leaves the block as it was. `ci` fails with the new verdict `not-run`, exit 3, when a spec has blocks not run beyond `--max-not-run` (default 0; the action input `max-not-run`). Core exports `blockStatus`, `isScored`, `runOutcome`, `blocksOutcome` (the outcome without the end verdict), `skipReason` (why a block was not run or blocked), `countRuns`, `countBlocks`, `unscoredText`, `capabilityGap` and the schemas `BlockStatus`, `NotRun`, `Blocked`; report exports `scoredRuns` and `unscoredRuns`. The scorecard page rates runs and blocks over the scored ones (pass plus fail), and so do `monitor --metric pass_rate`, `compare --rank` and the viewer index. The scorecard page and the run page give such a run or block its own badge (`not run`, `blocked`) with the reason, and count it apart from the failing ones. A not-run block carries the block provenance stamp, so a run that holds one can still be re-judged on its scored blocks. In mode T the canonical history the runner builds from the blocks before needs `seedPrefix` too: on `nexus` and the live Claude Code adapter every block after the first is `not_run`, never run without its history (no recorded mode T result of either is in the repository; of the shipped specs, block 1 of the three live estate `stop_resume` helper specs). The `process` adapter now declares `seedPrefix`: it always handed the agent the session history, prefix included, in `driftbench-history.json`, so its blocks with a prefix run as before. The store and bundle schema is 3, one bump for these verdict fields and the resolution fields `by`, `resolved` and `diagnoses`, with no table change: an older driftbench refuses a schema 3 store or bundle with the upgrade message, and a schema 2 store is upgraded on open. The vitest plugin skips a block test that was not run or blocked, with the check and the reason, as the JUnit report does; it never reads as a block the agent failed. The test generation gate leaves a fault agent that did not run a block out of the block's difficulty, of its kill counts (`KillCount.notRun` counts it) and, when it ran no targeted block, of its class score. `replay`, `estate live`, `simulate`, `perturb` and `family verify` count a spec or block that was not run apart and name the reason; the estate regression compares no run that was not run on either side (`not_measured`, never `pass_to_fail`). Reliability lines (`unscored`), the spread (`unscored`), `compare` (`excluded`), `compare --rank` (`notRun`), the `monitor` series (`unscored`) and the viewer index say how many runs they left out. Holdout, the pilot, estate decay, tool accuracy, the run panel, the succession drift rate and recovery count scored blocks only. Every reader of a block's pass or status goes through `blockStatus`, `isScored`, `skipReason`, `runOutcome` or `blocksOutcome`, and in the Python client through `verdict_of`; a test finds a direct read by type (the TypeScript checker over every package; an `ast` walk over the Python client), whatever the variable is named. The `BlockResult` schema refuses a block whose `pass` and `status` disagree (status `pass` with `pass` false, `fail`, `not_run` or `blocked` with `pass` true), on write and on read; a block with no status stays the runner's normal form. The gate keys the agents that did not run a block by role (`BlockRecord.notRun` is `{ reference, trivial, faults }`), so a fault id never stands for the reference. A recovery stored on a run whose injected block was not sent is no measurement: the report leaves it out and draws no recovery row for a deviation class with none. The pytest plugin skips a spec whose cells were only not run or blocked, with the reason (`run_specs` takes the command's exit 3 as a result, read as not run), and the Python client reads `status`, `notRun`, `blocked` and the summary's `notRun` and `blocked` counts. `family verify` counts an instance the reference cannot run apart as unverified (`unverified`; not shipped, never called a reference defect), and `campaign rejudge` names each block not run or blocked with its reason and counts its runs (`runs.notRun`, `runs.blocked`); both exit 3 when nothing failed but something was not run. * `radius localize` (phase 6 of the block redesign): ranks the local sections of a prompt by Ochiai suspiciousness from a stored campaign's block verdicts and the blocks' section links, with soft weights over repeats, tie ranges, and global sections left out. It follows the H5 rule: a failure is dropped only when an earlier block of the same conversation, or a parent block, failed in the same run; a passing block after a failing one stays a row. On the stored H7 runs it ranks the planted section worse than flat counting on 3 of 98 faults, against 18 of 98 for dropping every later block. * Advisory section selection (phase 6 of the block redesign). The change manifest gains the kind `prompt_section` (`<prompt-id>#<section-id>`); `radius sections reanchor --change-out` writes one per edited or reordered section and a global `prompt` change for text outside every section. A `prompt_section` change makes the radius the whole suite, so carry, `ci --change` and block reruns run every block. `radius --sections <registries>` prints which blocks selection by section links would run (links into the changed sections and their `references`, `overrides` and `duplicates` closure, blocks with no or stale links, every later block of the same conversation and descendants across parent edges) and which it would skip; JSON gains `advisory`. Re-scored on the stored H7 runs this rule reproduces the research numbers: 3 of 90 and 9 of 110 mutants missed with links alone, 2 of 90 and 4 of 110 with the forward closure. New examples in `examples/acme/prompts/linked`. Core adds `sectionSelection`, `sectionChangeManifest`, `sectionChanges`, `defaultParentOf`, `SECTION_SELECTION_ADVISORY` and their types to the frozen API list.
